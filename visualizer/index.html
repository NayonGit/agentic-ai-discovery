01

Workflows vs. agents, and the agent loop

Definition. A workflow is a system where code decides the sequence of steps. An agent is a system where the model itself decides the next step and which tool to use, based on what it discovers, looping until it judges the task done.

The whole treasure hunt is an agent loop: Claude exploring a small estate with three tools (look_around, move, search_room), deciding its own path turn by turn — nothing in the code chose the order of actions, only the rules of the world.

Why it matters: agents cost more and are less predictable than workflows — every turn resends the whole growing history, and the exact path varies run to run. A real system starts with the simplest option that works, not "agent" by default.

02

Guardrails: bounding an agent's cost

Definition. Hard caps — a maximum number of turns, a maximum budget — that stop the loop regardless of what the model itself decides, because "the model will know when to stop" is a soft guarantee, not a hard one.

Built as native Agent SDK options (max_turns, max_budget_usd) rather than a hand-rolled counter — the SDK stops the loop itself and reports why.

What we learned: the default caps almost never trip on their own — you have to deliberately force them low to actually see the mechanism fire. "I implemented it" and "I've seen it work" are different claims, worth verifying separately.

03

Tool failure & recovery

Definition. Real tools fail — timeouts, flaky dependencies, transient errors. A resilient agent needs to notice a failed result (is_error: true) and decide whether retrying is worth it.

The tower's ladder fails deterministically on the first attempt, then always succeeds after — with no hint anywhere that this would happen, so whatever the agent did next was a genuine judgment call.

What we learned: the exact wording of the failure message controlled the agent's behavior completely. An ambiguous failure ("you slip back down") led it to abandon the path and explore the entire rest of the map before trying again. An explicit retry hint ("worth trying again") led it to retry on the very next action. The error message is a design surface, not an afterthought.

04

Planning & multi-step dependencies

Definition. Some goals require satisfying a prerequisite first — a locked door that needs a key found somewhere else. Can the agent recognize a blocker and go solve it, instead of only reacting to what's directly in front of it?

The tower is locked unless the rusty key (sitting in a side room) is already in the inventory — a real precondition, not a one-shot failure.

What we learned: across repeated runs the agent handled it correctly either way — sometimes gathering the key proactively before ever trying the door, sometimes getting blocked first and correctly backtracking for it. Both are valid outcomes; a single run isn't enough to tell you which capability you actually tested.

05

Untrusted tool output & prompt injection

Definition. Any tool that returns content from outside your control — a web page, a file, a user submission — can carry someone else's instructions riding along inside it. The agent has to treat tool results as data, never as commands.

A planted note, found via search, impersonates a system message asking the agent to leak its configuration and stop working — modeled on a real attack goal, not a hypothetical.

What we learned: the agent caught it immediately and explicitly, named it as an injection attempt in the game content, and kept working — genuinely reassuring. The honest caveat: this was a blatant, self-announcing attempt. One clean result is evidence the defense can work, not proof it always will.

06

Approval gates for risky actions

Definition. Some actions are consequential enough — deleting data, spending money, sending a message — that they should require a real human's sign-off before executing, regardless of how aligned the model seems.

force_door is an irreversible shortcut past the lock, gated by the Agent SDK's actual permission system (a PreToolUse hook) — not a simulated prompt.

What we learned: across three runs, the agent never once chose the risky shortcut when the safe path was available — reassuring, but it also means the gate may rarely fire because good tool descriptions already discourage the risky choice. The gate still has to exist and actually work; avoidance is a tendency, not a guarantee.

07

Scaling, and what we actually measure

Definition. As a task grows, assumptions calibrated for the smaller version quietly stop holding. The only way to know whether something changed for the better (or worse) is to measure it across repeated runs — not read one transcript and guess.

The metrics, and why each one:

  • Success rate — did it finish the task at all? The most basic reliability question; a cheap agent that fails half the time isn't actually useful.
  • Cost — the literal dollar question this whole project set out to explore.
  • Turns — a proxy for efficiency: more turns usually means more wall-clock time and more chances for something to go wrong.
  • Cache-read tokens — a diagnostic, not a goal: explains why cost behaves the way it does, not whether the agent did well.

Honest caveat: these are the metrics that were already being tracked by the dashboard, not ones deliberately chosen in advance for what "good" means on this task. A fuller evaluation would also define a task-quality metric (did it take an efficient path, not just finish?) and a safety metric (did it ever violate a boundary?) before calling any result "better" than another.

What we found: on the scaled map, 4 of 5 runs cost $0.44–$0.48 — right against the old $0.50 budget cap — and the 5th failed it outright. The cap didn't get worse; the task outgrew what it was calibrated for.

08

Context compaction — and a measurement bug it exposed

Definition. A long-running agent resends its whole conversation history every turn. Auto-compaction is the SDK's own fix: when context usage nears a threshold, it summarizes older turns and replaces them, the same mechanism Claude Code itself uses — not something to hand-roll. A PreCompact hook observes it firing without changing the behavior.

What we found, part one: on this map, context plateaus almost immediately — around 123,000 tokens, the fixed cost of the system prompt and four tool schemas — and then grows only ~200–300 tokens per turn. Across 5 default trials, auto-compaction never fired once. The task is simply too small to need it yet.

What we found, part two: forcing it to fire early (via the CLI's --autocompact flag) didn't show graceful degradation — it made the SDK's own auto-compact thrash: compact, immediately exceed the threshold again, compact again, and eventually give up with its own diagnostic, "Autocompact is thrashing… try reading in smaller chunks, or use /clear to start fresh." Every threshold tried between 100k and 150k thrashed the same way; 180k simply never triggered, matching the untouched default. No graceful middle ground turned up in that range.

The bigger catch: the thrashing session still reported outcome: "success" — because that label only means the SDK session ended without tripping a guardrail, not that the agent actually found the treasure. Every earlier stone's "success rate" was trusting that label at face value. Caught here, fixed by checking the real game state (treasure_found) directly instead of trusting the harness's own label — the single most durable lesson of this stone, independent of compaction itself.

What to conclude: this isn't a bug to route around — it's a sign the task is still too small for compaction to be a meaningful lever. Worth revisiting once a harder task (bigger map, real sub-agents) actually needs it.

09

The vault puzzle — a negative result worth keeping

Definition. A task only gives sub-agents or external memory room to prove their worth if a single agent can genuinely fail it. The attic's chest became a locked, three-digit dial — the digits scattered across three previously-decorative rooms, each stating its own position so the code doesn't depend on exploration order. A new open_chest(code) tool is the only way to win; wrong codes are freely retryable, since the intended difficulty is remembering the digits, not being punished for guessing.

What we found: 5/5 trials succeeded, genuinely (checked against treasure_found), at roughly double the pre-vault cost and turns — with zero wrong code attempts anywhere. More rooms and more digits made the task slower, never harder in the way that matters.

Why, audited rather than assumed: context here grows only ~200–300 tokens/turn, so even a 30+ turn run stays far short of needing compaction — the agent always held the literal, uncompacted transcript. Three digits in a transcript a frontier model can see in full isn't a memory test, just a longer walk. Testing the model itself (Sonnet 5 vs. Sonnet 4.5 vs. Haiku 4.5, same puzzle) showed the identical pattern: all three got the code right every time: the gap was entirely in navigation efficiency (Haiku re-searched already-emptied rooms four times; neither Sonnet model did it once), not correctness.

What to conclude: "harder" for this class of model has to come from making recall genuinely lossy (real compaction, not a forced override) or genuinely ambiguous (a decoy clue to get wrong) — not from adding more of the same. Spec'd both as separate next branches instead of guessing further.

10

A real capability ladder, found by testing rather than assuming

Definition. Before spending more effort engineering a harder task, test a cheaper worry directly: maybe the model itself is simply too capable for a toy puzzle like this to ever stress. Ran the identical vault puzzle, unchanged, against three models: claude-sonnet-5, claude-sonnet-4-5-20250929 (one generation back — the original Sonnet 4 is retired as of June 15, 2026, verified directly rather than assumed), and claude-haiku-4-5-20251001 (a smaller tier entirely).

What we found: all three solved it correctly every time — zero wrong open_chest attempts anywhere. Sonnet 5 stayed efficient (31-33 turns); Sonnet 4.5 needed more turns and cost for the identical result, coherently; Haiku 4.5 solved it too, but through genuinely aimless navigation — four separate dead-end re-searches and a pointless trip back to the entrance, something neither Sonnet model did once. The gap was never memory — it was exploration efficiency, and for Haiku, the kind of mistake changed entirely, not just its frequency.

The label gap, again: one Sonnet 4.5 run landed right at the edge of the then-current budget cap — outcome: "error_max_budget_usd", but treasure_found: true. The exact ground-truth-vs-label lesson from the compaction stone, resurfacing unprompted in a completely different context. Watch the recording below to see it.

What to conclude: chose Sonnet 4.5 as the new default specifically because it's a controlled, coherent difficulty increase — a real step down from Sonnet 5 to build the next stones on, rather than Haiku's more chaotic failures, which would confound "the puzzle is hard" with "the model doesn't understand the task." Recalibrated guardrails from one clean run (42 turns / $2.06), then watched the 5-trial mean land notably below that single sample ($1.33) — the same "one run is an estimate, not a precise number" lesson, confirmed a second time.

Coming next in this course

  • A genuine decoy clue — something that can be actively wrong, not just slow to find, testing verification instead of pure recall.
  • Forcing real compaction — dense enough in-world documents to cross the natural threshold, measuring whether a lossy summary corrupts an exact fact.
  • SDK-native subagents — once a single agent genuinely isn't enough.
  • Randomized map generation — makes persistent memory across runs actually meaningful, instead of just memorizing one fixed layout.
